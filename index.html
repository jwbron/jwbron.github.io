An AI code reviewer shaped by its users

Problem
Khan Academy was paying for a commercial review bot across its repositories.
What I did
Designed, rolled out and ran a replacement built on github actions and the claude agent SDK. Specialized reviewers each looked for different problems, findings were checked before they reached anyone, and follow-up reviews only looked at what had changed since the last pass. Engineers' feedback shaped how it worked.
Result
About a fifth of the commercial bot's cost, with deeper, better reviews.

Execution boundaries for coding agents

Problem
Coding agents need real tools to be useful, and real tools are risky in the wrong hands.
What I did
Built agent harnesses, the systems that control an agent's tools, permissions and execution. Agents ran in OS-level sandboxes, credentials stayed with a broker instead of the agent, and permissions were scoped to the task. Required workflow checks were enforced in code, and tooling failures the agents reported went into a shared backlog with people triaging the unclear ones.
Result
Agents could do real work inside limits that didn't depend on them following instructions.

Evaluations that showed what was failing

Problem
Choosing models and agent setups by impression is guesswork.
What I did
Built evaluation infrastructure, repeatable tests of how agents perform, with A/B runs, regression monitoring, transcript capture and cost tracking by model.
Result
Harness and model choices rested on evidence, and we could tell a model failure apart from a problem in the test setup or scoring.

How I work

Remove the capability, don't add a rule. If an agent mustn't do something, the tool or permission shouldn't be there. A prompt shouldn't be the only thing in the way.

Agreement isn't evidence. Findings need receipts from real artifacts. I once watched eight out of eight AI reviewers sign off on code that didn't build.

Measure before choosing. Repeatable evaluations beat impressions when picking a model, a tool or an architecture.

Do the boring work that compounds. Pipelines, migrations and runners rarely make a demo, but every engineer feels them every day.
