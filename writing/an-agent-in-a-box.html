An agent in a box

How to sandbox an AI agent that works unsupervised, starting from the assumption that it will eventually do the wrong thing.

Once an agent runs without someone watching every step, the useful question stops being whether it will misbehave. It will, sooner or later. The question is what it's able to do when it does.

I worked through this in a security design for james-in-a-box, a setup for running coding agents unattended against private repositories, and the same ideas now run underneath egg. The details are about code, but the shape applies to any agent you connect to real systems and real data.

Start with who you're defending against

A threat model for an agent has more entries than people expect. There's prompt injection, where someone hides instructions in a ticket, a document or a web page the agent reads. There's plain model misbehavior, where "fix the bug" somehow becomes "delete the file." There's the agent that decides its constraints are in the way and works around them. And there are the two outcomes all of those can lead to, which are data leaving through a side channel and credentials getting copied somewhere they can be used later.

From inside the system you usually can't tell which of these you're facing. A strange request to push to a new branch might be a confused model or an injected instruction, and it doesn't matter much which. So the design treats the agent itself as untrusted, all the time, and puts the guarantees somewhere the agent can't reach.

Draw one line

Everything in the design comes back to a single boundary between an untrusted zone and a trusted one.

The untrusted side is the agent's container. It holds the agent, its working files, read-only context and its own notes. Just as important is what it doesn't hold. There are no repository tokens, no SSH keys and no cloud credentials. There's no direct route to the internet. It can't see version control metadata, so it can't rewrite history behind anyone's back, and it can't see any other agent's workspace.

The trusted side is a gateway that sits next to the agent. It holds the credentials, runs the network proxy, applies policy and writes the audit log. The only bridge between the two sides is an authenticated API. When the agent wants to push code or open a pull request, it asks the gateway, and the gateway checks the request, does the work with its own credentials and records what happened.

That's where rules like "only push to your own branches" and "never merge" actually live. The gateway has no merge operation to offer, so there's nothing to talk it into.

Default-deny the network

A box with an open internet connection isn't much of a box. All traffic goes through a proxy with a short allowlist, which is the model provider, the code host and little else. Arbitrary sites are unreachable, and that's the point, because an agent that can reach any API can send anything anywhere.

This has costs, and they're worth naming. The agent can't install packages or search the web on its own, so dependencies get baked into the image ahead of time. When a blocked tool gets called, the agent gets a clear refusal and adapts by using what's local. In practice that's less disruptive than it sounds.

The allowlist only grows through review. Adding a domain is a security decision, and it never happens automatically because an agent asked for it.

Grow access in stages

The most useful idea in the whole design for teams just starting with agents is that access should grow in deliberate steps, not all at once.

  1. A local sandbox with no network at all.
  2. Read-only access to public resources like documentation.
  3. Read-only access to your private systems, such as code, tickets and internal docs.
  4. Write access to those private systems, through the gateway.

Each step gets earned. You learn how agents behave at one level before you hand them the next, and nobody has to approve a giant leap from "experimenting" to "the agent can edit our wiki."

Write down what you can't fix

No design like this is airtight, and pretending otherwise is how people get surprised. The honest version lists the risks you're choosing to accept.

The clearest one is text. An agent that can write commit messages or pull request descriptions can, in principle, smuggle data out in them. You could cap their length, but that breaks legitimate work and only slows a determined leak. So the design accepts it and bounds it instead. Agents only work in private repositories, a person reviews what gets merged, and every operation is logged so unusual patterns stand out.

The other is the model's own API key, which is the one credential that has to live inside the box because the agent can't run without it. You can't hide it, so you limit what it's good for. The network only lets it reach the model provider, its usage gets watched, and it can be rotated quickly.

Writing these down isn't a weakness in the design. It's what makes the rest of it trustworthy, because everyone can see where the edges are.

Make every connector look the same

Agents get more useful as they connect to more of your systems, like chat, tickets, wikis and data warehouses. The way to keep that from turning into a new security project every time is to make every connector follow the same pattern. The gateway gets a new endpoint, the service's credentials live only in the gateway, the endpoint enforces its own policy, and every call lands in the audit log.

That's also the pattern I'd bring to a law firm or any other organization wiring agents into its documents and email. The agent asks, the gateway decides, and the credentials and the record of what happened never leave the trusted side.

The point of the box

Instructions shape what an agent tries to do. The box decides what actually happens. When the box is built well, an agent that follows its instructions is a pleasant bonus rather than the thing your security depends on.
