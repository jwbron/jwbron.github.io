Intentional agentic work · Control

The model owns judgment, code owns the clock

Models are good at judgment and unreliable at bookkeeping. Give each job to the thing that's good at it.

Agents in a real workflow spend a lot of their time waiting. They wait for a review, for another agent's work, or for a person to answer a question. Left to manage that themselves, models improvise, and they improvise from whatever their training data suggests, which means sleeps, polling loops and repeated status checks.

In early versions of a system I built, where agents owned their own waiting, all of these showed up. One agent announced it was finished more than twenty times in a minute and a half. Another polled on a fixed schedule and missed an objection that had been sitting there for several minutes. Another waited for a signal that only its own next action could produce, and sat deadlocked for about half an hour. None of these are reasoning failures. The model was being asked to do bookkeeping, and bookkeeping is the thing it's worst at.

The seam you can't prompt away

There's a deeper problem underneath. If an agent has to hold a waiting loop and re-enter it after every step, then every re-entry is a point where it can simply stop. It writes a final message, and the loop is over. One model would reliably come back. Another model, given the same instructions, often didn't. You can tune a prompt until a particular model behaves, but you've only fixed it for that model, and only until the next release.

Turn it inside out

The fix is to stop asking the model to run the loop at all. Instead, a plain, deterministic orchestrator owns sequencing. It reads the current state of the work, works out what should happen next for each role, and waits when nothing needs doing. When something does, like a proposal to review or an objection to answer, it starts a fresh agent for that one event. The agent does its job, records its judgment and exits.

A role is finished when the orchestrator records that it's finished, not when a model decides to stop talking. Nothing depends on the model choosing to come back, so there's no seam to fall through, and it works the same way regardless of which model is running.

A few details keep this honest. Before acting, each agent checks once more that its event is still current, so if someone else already handled it, it skips. At most one agent runs per event. And continuity doesn't come from a long-running session. It comes from a short memory file for each role plus the protected core described in Reseed, don't compact, so a brand-new agent can pick up a review cycle exactly where the last one left off.

Quiet isn't failure

Once the orchestrator owns the clock, it also has to decide what to do when nothing happens for a while. The obvious answer, which is to restart things a few times and then give up, turned out to be wrong. Some phases are legitimately quiet for a long stretch, and a restart cap would eventually kill perfectly healthy work. So idleness doesn't fail anything. Past a time budget, the orchestrator alerts a person, raises the priority if it keeps going, and keeps running. A person decides whether quiet means stuck.

Monitoring follows the same rule

My first monitor for this ran a model over every observation. It was loud, with a steady stream of high-priority alerts that weren't real, including one where it mistook its own startup for an attack. People learned to ignore it. It was also useless at the moment it mattered, since real deadlocks showed up as vague alerts, or not at all.

The rebuilt version splits the job three ways. Deterministic detectors watch for problems they can prove, and the vast majority of observations end there, with no model involved. A model is only consulted on the ambiguous minority, and it advises rather than acts. A separate control plane carries out its advice, choosing from a short, fixed list of actions: nudge an agent, restart a group, or ask a person. Every action is deduplicated, rate-limited and logged. The advising agent can't open a decision on a person's behalf. Only the control plane can, through a path that's bounded and audited.

Beyond code

Most firms already run on this split. Deadlines, routing and reminders live in a case management or workflow system, and people bring the judgment. An agent drafting or reviewing inside that workflow should be treated the same way. The system tracks the deadline and hands it the next document, and the agent decides what the document needs. Nobody should be relying on an AI to remember to check back on Thursday.

Models are remarkable at judgment and unreliable at bookkeeping. Let code keep the clock, and call the model when there's something worth deciding.
