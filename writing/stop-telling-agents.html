Stop telling AI agents what not to do

A prompt that says "don't" is a suggestion. Take the capability away instead.

James Wiesebron · October 22, 2026 · Examples from my personal research systems

When people start putting AI agents to work, the first safety tool they reach for is the prompt. Never merge a pull request. Don't touch the production database. Don't email the client. Almost every team starts there, and it holds only as long as the agent keeps following it.

A prompt is a suggestion. It's one more thing in the agent's context, weighed against everything else it's trying to get done. A few hours into a long task, with your instructions buried under a pile of newer messages, an agent that was told never to merge can decide that merging is obviously the helpful thing to do. And if someone slips their own instructions into a document the agent reads, your prompt is the first thing they'll talk it out of.

Writing the rule in capital letters doesn't change any of that. The agent can still merge. You've just asked it very nicely not to.

Take the door away

In the agent systems I build, agents can't merge at all. Everything they do with git and GitHub goes through a gateway that lives outside their sandbox, and that gateway doesn't have a merge operation. There's no flag that unlocks it and nobody to talk into it. If an agent tries, it's told that merging isn't something it can do, and that a person has to.

Credentials work the same way. There are no tokens or keys anywhere in the agent's environment. They get attached to requests on the way out, after the agent is done with them, so the agent can't leak something it never had. "Don't print your API key" stops being a rule you have to hope it follows.

Once you start looking at problems this way, a lot of rules turn into missing doors. Agents can only push to their own branches. An agent that's planning can't write code, and an agent that's writing code can't edit the plan it was handed.

Let the wall explain itself

When an agent bumps into a limit, what comes back should tell it why, and what to do instead. If it pushes to the wrong branch, the error spells out the naming convention, and it fixes the mistake on its next try.

That works far better than cramming every rule into the system prompt up front. The agent doesn't spend attention on rules it may never need, and when it does need one, the explanation shows up right when it matters, not fifty thousand tokens ago.

Sometimes the best version is one the agent never notices. GitHub won't let a bot approve its own pull request, so the system turns those approvals into comments and keeps the verdict. The agent gets what it was going for, and nobody wastes a retry.

It isn't just about code

The same idea carries straight over to agents doing everyday knowledge work. Say a team wants an agent that drafts replies from a shared inbox. You could tell it never to send anything without sign-off. Or you could give it a connection that can read and draft but has no way to send, and let a person press the button. Only the second still holds when the agent gets confused, or when someone emails it a cleverly worded request.

Connectors with enforceable boundaries covers how to build connections like that, and how to treat what comes back through them.

If you catch yourself writing a sterner prompt to stop an agent from doing something, take the ability away instead.
