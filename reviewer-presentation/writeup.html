Attention is all you need (to protect)

Reducing cognitive burden on developers with a custom AI review system.

James Wiesebron Founding engineer, AI Developer Experience, Khan Academy · October 2026

By the end of this project, every pull request in Khan Academy's frontend and backend monorepos got a thorough first pass from an AI reviewer, on every push, before a human approved it. About 120 engineers worked in those repos, opening dozens to low hundreds of PRs a day.

The review quality was good early. Most of the work went into three other things: keeping cost low enough to run on every push, cutting the comment volume until engineers wanted it on, and checking that the system actually did what it said it did. All three came down to one goal, which was taking load off the developers using it.

Review became the bottleneck

AI made code cheaper to write. Khan had encouraged every engineer to try AI tools, they did, and the number of pull requests went up.

Review didn't keep up. Reviewers got tired, and quality got uneven, since AI use was uneven on both sides of a review. The worst case was a reviewer who wasn't using AI much, reading a PR from an author who wasn't using it well either.

Compliance still requires a human approval on every merge, so replacing the human reviewer was never an option. The goal was for every PR to already have a thorough review by the time a person opened it.

We set four goals for the reviewer, all about the people using it: less cognitive burden on developers, a higher quality bar for PRs, reviews that were consistent no matter who wrote or reviewed the code, and a team that could ship faster without worrying about what slipped through.

What we had before

We already had two AI reviewers. Claude Code's managed review was good, but too expensive to run on every PR and every push, so it only ran when someone asked for it. My estimate is that running it on everything would have cost about five times what our reviewer ended up costing. Engineers also found its comments hard to read.

Khan also had a lightweight triage bot. It was cheap on purpose: it looked for a few specific things and told the human reviewer where to focus. It was never meant to be thorough.

Neither one gave every PR a thorough first pass that knew Khan's own standards. I looked at open source review systems and didn't find anything mature or flexible enough, so I built on the existing triage bot.

Getting three groups to say yes

I started with a written proposal, "more depth, less noise." It opened with what already worked in the existing design: a triage pass, focused sub-agents, and a validator that double-checked claims before posting. Then it described the gap. On the first PR I traced, the reviewer never raised an authorization question that the repo's own risk config rated High, because the prompts leaned so hard toward precision that it dropped anything uncertain.

The proposal also asked who would own the reviewer as a product, since an internal tool nobody owns ends up maintained in people's spare time. I took it on.

Three groups had to agree. Technical leadership had to sign off on the direction, every change I made went through review, and cost was the main concern going in. Engineers had to want it on their PRs, and in the end that's what decided the switch. And it had to fit the budget. I owned AI spend and my manager approved increases, which was an easy conversation once the cost per PR was low enough to run on everything.

The plan

The proposal split the work into four phases, cheapest first. Evals gated only the changes that could regress, so the cheap fixes shipped right away.

Phase 1Quick fixes that couldn't break anything, plus a feedback loop
Phase 2A small benchmark, then noise controls
Phase 3The full eval suite and deeper reviews
Phase 4Hardening, then deciding on default-on

Some work was worth doing but not needed to launch, so I put it off: a weekly feedback report, gathering context across repos, unattended fixes, and moving off GitHub Agentic Workflows. That kept the launch small.

How a review runs

A PR opens or gets a push. Code, not a model, picks which specialist reviewers to run, based on what changed.

A full review runs about a dozen specialists: correctness, tests, docs, security (on repos that turn it on), a holistic pass that reads the whole change, and audits against Khan's own best-practice skills. Each one looks for one kind of problem, which is where the depth comes from.

Their findings get validated and deduplicated before anything posts.

Code then computes the verdict and writes the comments. The verdict is advisory, since a human always approves the merge.

On a new push it doesn't start over. It checks whether the open comments were addressed, resolves the ones that were, and only reruns the full review if the diff changed a lot. This ended up being the biggest cost saver.

None of the agents had credentials or permissions. They read what the pipeline gave them (source code, tickets, PR descriptions and comments) and wrote their results back. The pipeline held the credentials and posted the review. Security reviewed the setup before launch.

The first week: good catches, way too many comments

I trialed it on my own team's PRs first, alongside the managed review, and anyone else could run it by commenting on a PR. In its first week with real users it caught real problems, including a cross-package compile break. The volume was the problem. One PR got seven non-blocking comments on a single push and five more two days later, and the recap re-listed every open thread each time.

Engineers said the nits and questions were the main issue, and the frontend infra team turned auto-review off.

Attention was the thing to protect, and every extra comment spent some of it.

The fixes shipped within about a day. Blocking findings always post. Non-blocking ones are ranked and capped at three, nitpicks never post inline, and the rest go into a collapsed section, so nothing is lost and the notification stays short. Re-reviews only look at what changed.

The comments themselves changed too. Each one became two layers: a short comment written for a person, with the model's fuller reasoning collapsed underneath for agents. Scripts enforce that format, and a separate model grades the writing.

Fixes only run when the author asks, by replying "ship" on the comment. Nobody had to install anything or change how they worked.

Anything that could regress went through evals

Changes that could regress went through an eval bench first: real PRs plus planted defects the reviewer had to catch, run as A/B comparisons. We also ran identical versions against each other to measure the noise, so we knew how big a difference had to be before it meant anything.

Against a generic reviewer on the same PR, all of our extra catches came from the audits against Khan's own skills, like a swallowed error and a fetch that loaded whole entities when it only needed keys. A reviewer that doesn't know the codebase can't catch those.

The eval itself needed checking too. One case looked flaky, so I read all 28 runs. The reviewer had found the defect in every one, and the scorer only accepted one source location. Fixing the scorer changed the numbers without changing the reviewer, which is why I read transcripts before trusting a score.

2 of 5 runs skipped dispatch and still looked fine

Early on, the orchestrating model was told to dispatch the specialists and validate their findings before posting. In a seeded trial, all five runs posted a review that looked fine.

Two of them had skipped dispatch and written the review themselves. Nothing in the output showed it. Our scripted eval missed it because its own dispatch was already deterministic.

So I moved staging, dispatch and submission checks into code, and scripted dispatch became the only mode.

About a fifth of the managed review's cost

Cost was the main concern going in: would a dozen reviewers make reviews expensive and long? The triage bot is the baseline here.

The full first-pass review ended up at about 2.2 times the triage bot's cost. Moving dispatch into code paid off here too. Turns out most of the cost had been the orchestrating model deciding what to do next, not the reviewers, and with that work in code its share went from about 80 percent of a review's cost to about a quarter. Re-reviews were the other big cost, and checking only the open comments cut a repeat round by 82 percent.

Running the managed review on every PR and push would have been about 11 times the baseline, roughly five times what we spent, using the same models. That's an estimate, since it only ever ran on request.

Things I didn't build

I built a panel of skeptic agents to double-check blocking claims, then took it out. An audit of every blocking review over about a week (90 PRs) found 12 false blocks, and only 2 were the kind another verification layer could catch. The rest were wrong severity calls and questions about what the author meant. Stricter claim validation, with no extra agents, handled it.

I proposed a stronger model for five reviewer roles. Review pushback was that five was overkill, so I tried it on the correctness reviewer alone, where recall went from 82 to 89 percent on the eval set for 35 percent more cost.

A cheaper model was worth testing. It caught 32 of 36 required findings against 36 of 36, and at our actual rates it didn't save money either. That's from one full repeat, so it isn't a benchmark, but it settled the question. The transcripts also showed that some apparent model failures were problems with the test setup: different hidden reasoning defaults, an eval that let the model go looking for answers, and scoring bugs.

Blocking merges was off the table, since compliance requires a human approval. Fixes ran only when an author asked, and each specialist stayed opt-in per repo until it earned its place in evals.

Launching to everyone

The triage bot was already running in the frontend monorepo. After the proposal, the trial ran on my own team's PRs for a few weeks, alongside the managed review.

Then the first week with real users, and the quieter version a day later.

While review was still opt-in, a PR that skipped it caused a production incident. Afterward I ran the reviewer on that merged PR, blind, with no context about the incident, and it flagged the problem. One case doesn't show it prevents incidents, but it's why we turned it on by default.

Before default-on, I wrote a launch brief that set the success criteria ahead of time: no incident affecting authors, and noise reports staying at trial levels. It had three levels of rollback (a label to skip one PR, a kill switch for the repo, and a single revert). The opt-out label existed, but we didn't advertise it. Once technical leadership approved the brief, the reviewer went on for every author in the backend monorepo, then frontend after a clean week, and stayed the main reviewer for a couple of months. The frontend infra team turned it back on.

How the work ran

Agents wrote the code, and I made the decisions about what shipped. I wrote the specs and plans, validated results, and read the sensitive parts myself, like the verification logic and the cost caps.

To keep my own understanding current, agents checked each handoff: plans against the original spec, the implementation against the plan (no unexpected additions), and the docs against the implementation. Agents made mistakes constantly, so the process assumed they would. Review agents posted findings, my local agents fixed them, and the change went back for review until it passed. The reviewer also ran on its own repo, so it reviewed the changes to itself.

I was on call for it during work hours. A pipeline read every reply to the bot's comments, decided whether it pointed at a real problem, opened or updated a ticket, and pinged me, so engineers never had to file anything.

Reviewers told us they spent less time per PR, because PRs came in cleaner after the first pass. They needed fewer rounds of human review, and time to merge dropped. Those are reported, not measured. A before-and-after analysis was next on the list.

What we did measure: it replaced the managed review and reviewed every PR and push. Noise reports stayed at trial levels after default-on. Engineers who had used both said ours was more thorough and easier to read quickly.

What I'd do differently

I'd have moved off GitHub Agentic Workflows (gh-aw) sooner. It came with the first version and got us running fast, which was the right call at the start. Once we needed the reviewer to do things gh-aw wasn't built for, every change needed a workaround, and we couldn't run the reviewer locally.

The next steps from there were our own harness, the model out of orchestration entirely, one review engine across CI, a local CLI and a pi plugin, and a real before-and-after measurement of time to merge.

Rules I still use

Anything that has to happen goes in code, and the model gets the judgment calls. Agents don't hold credentials, the pipeline does. The tools you measure with need checking too, since a broken scorer looks exactly like a weak model.

And protect people's attention. The people using a tool decide whether it works, so build it around how they already work.

Keep it quiet unless it has something worth saying.
